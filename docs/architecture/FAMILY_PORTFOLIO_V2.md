# 가족·다계좌 포트폴리오 v2

기본 진입 화면은 회원 본인 명의 계좌입니다. 가족 추가·관리는 접힌 선택 메뉴에서 열고, 가족 포트폴리오를 선택할 때만 가족 계좌와 가족 합계를 표시합니다. 신규 회원은 가족 이름·가족 구성원을 먼저 입력하지 않고 본인 계좌부터 등록할 수 있습니다. 최초 계좌 등록 시 서버에서 사용자별 개인 공간과 본인 프로필을 한 번만 생성하며, 기존 가족·계좌 데이터와 권한은 유지합니다.

## 조사와 영향

- Vue 3 / Vite / Vue Router, PrimeVue, Firebase 이메일·비밀번호 및 Google 인증. Firestore Admin Python Flask API와 브라우저 Firebase SDK를 함께 사용하던 구조.
- 기존 `/mypage`는 `portfolios/{uid}/assets/{asset}/transactions`와 이전 저장소를 읽는다. 명의자·계좌 식별이 없어 같은 종목의 다른 계좌 잔고가 합쳐질 수 있고, 거래 기간 이전 취득분을 복구할 수 없다.
- 기존 PDF importer는 미식별 행·미매핑 종목을 제외하고 계좌 확인 없이 저장할 수 있었다. 새 `/mypage`는 가족 흐름으로 교체하고 이전 화면은 `/mypage/legacy`에서 읽기만 제공한다. `/api/portfolio-import`는 410을 반환해 이전 클라이언트의 단일 계좌 저장을 막는다. 기존 읽기 서비스·데이터는 삭제하지 않았다.
- 공개 시세·배당 수집, 썸네일 계산, 콘텐츠 파이프라인에는 변경이 없다. 종목 상세의 개인 투자 현황은 새 계좌 잔고를 사용하고 근거 없는 현재 손익·FIFO 확정 표시는 제거했다.

## 구현 순서와 저장 구조

1. 가족 공간, 독립된 구성원 프로필, 로그인 사용자 참여 관계, 계좌 ACL을 도입.
2. 계좌별 미리보기 → 수정 → 검증 → 원자적 저장. 잔고와 거래 원장을 분리.
3. 가족·계좌 관리와 명의자·계좌·종목별 합산, 종목 상세 연결.
4. 이전 자료 보존 복사, 서버 경계 테스트, 브라우저 흐름·빌드 검사.

Firestore는 SQL 스키마 변경이 없으므로 `schemaVersion: 2` 컬렉션을 추가하는 점진적 마이그레이션이다.

| 경로 | 데이터 및 권한 |
| --- | --- |
| `familySpaces/{id}` | 이름, 공간 관리자 UID, 참여 사용자 UID 목록, 프로필 map. 성인 프로필은 본인 UID, 미성년 프로필은 보호자 UID와 확인 시각 |
| `familyInvitations/{sha256(token)}` | 48시간 1회용 참여 코드, 가족 ID, 만료 시각. 원문 토큰 저장 안 함 |
| `investmentAccounts/{id}` | 금융기관, 일반/ISA/연금/기타 유형, 별칭, 명의자 profile ID, 계좌 권한 위임 주체 authorityUid, 사용자별 owner/editor/viewer ACL, 마스킹 식별자, 기준일·출처, 최신 잔고 스냅샷 |
| `.../entries/{sha256(externalId)}` | 계좌별 거래 원장. 원래 거래 고유번호, 일자, 종목 코드, 수량/금액, 통화, 거래 유형, 출처·기준일·반영 시각 |
| `.../reviews/{id}` | 업로더 UID, 정규화된 편집 행, 파일 SHA-256, 기준일, 출처. 1시간 유효 |
| `.../imports/{fileHash}` | 계좌별 파일 반영 영수증. 반복 업로드 중복 차단 |
| `.../snapshots/{fileHash}` | 기준일의 전체 잔고 스냅샷. 최신 기준일만 계좌의 표시용 snapshot으로 선택 |
| `.../legacyAssets`, `.../legacyEntries` | 기존 자산과 거래의 보존 복사 및 원본 경로. 기준일 미확인 자료는 합산 제외 |

새 컬렉션은 Firestore 규칙에서 브라우저 직접 접근을 전부 막는다. 기존 `assets` collectionGroup의 사이트 관리자 규칙과 충돌하지 않는 이름을 사용했다. 새 API는 모든 조회·변경에서 Firebase ID 토큰(취소 여부 포함), 가족 참여, 계좌 ACL을 검사한다. 공간 관리자 권한으로 계좌 원장을 열거나 성인 명의를 대신 등록할 수 없다. 계좌의 명의자/보호자만 공유 설정을 바꾼다. 공유 편집자는 업로드만 추가로 가능하다. 초대 수락은 가족 참여만 허용하며 계좌는 별도 공유해야 한다. 초대 전달·메일 발송은 자동 수행하지 않는다.

`connection: {mode: 'file', provider: null}`는 향후 공급자 연결을 위한 경계다. 공급자 토큰이나 계좌 전체 번호를 여기에 저장하면 안 된다. 향후 별도 서버 전용 연결 컬렉션에 고객별 동의·암호화 자격증명 참조를 추가하고, 파일과 동일한 계좌 정규화/중복 검사 경로를 사용한다.

## 자료 정책과 기본값

- 성인 본인 참여는 실제 로그인 계정의 1회용 초대 수락으로 확인한다. 실명·실계좌 소유권을 증권사로 확인하는 기능은 없다. 보호자는 법정 보호자임을 명시적으로 확인한다. 성인 전환, 보호자 변경, 증빙 심사, 가족 탈퇴·삭제는 첫 버전에 없다. 임의로 보호자·명의자를 바꾸는 API도 없다.
- 프로필 최대 30명. 파일 2MiB, HTTP 요청 3MiB, 파일당 200행. 거래 원장 조회는 200행씩 다음 페이지를 읽으며 모든 페이지를 조회할 수 있다. CSV의 기간은 나눌 수 있으나 잔고는 해당 계좌의 전체 잔고여야 하므로 200개가 넘는 보유 종목은 첫 버전에서 지원하지 않는다.
- 업로드에서 기관·명의자·계좌와 자료 기준일을 사용자가 확인해야 한다. 파일 식별이 불확실하면 저장하지 않도록 안내한다. 자동 명의 추정이나 다른 계좌 자동 등록은 하지 않는다. 전체 계좌번호는 입력받지 않고 선택적으로 끝 4자리만 받아 `****1234`만 저장한다.
- 원본 파일과 PDF 비밀번호는 DB에 저장하지 않는다. PDF는 임시 파일에서 파싱 후 `finally`에서 삭제한다. CSV의 임의 추가 열은 검토 저장에서 제거한다. 만료 검토는 서버에서 즉시 거부하며 실제 삭제 시점은 Firestore TTL에 따른다. `firestore.indexes.json`에 reviews·familyInvitations의 expiresAt TTL 구성을 추가했다.
- 오류 행은 번호와 오류를 표시하고 전체 행 수정 후 다시 검증한다. 오류가 남으면 전체 반영을 거부한다. PDF 파서가 해석하지 못한 날짜 시작 행/텍스트 없는 페이지도 수정이 필요한 행으로 표시한다. 미지원 형식은 표준 CSV로 변환해야 한다.
- 거래와 잔고는 별도다. 매수/매도/배당/배당취소/현금 입출금/증권 입출고/분할을 원장 이벤트로 기록하지만, 거래로 잔고나 취득원가를 재구성하지 않는다. 이동을 수익으로 계산하지 않으며 이동 상대 계좌 자동 연결·배당 재투자·분할 원가 계산은 하지 않는다.
- 잔고는 기준일 전체 스냅샷이다. 오래된 잔고를 올려도 최신 잔고를 덮지 않는다. 같은 기준일에 다른 잔고를 올리면 409로 거부한다. 잔고 정정/삭제는 별도 정책과 기능이 필요하다.
- 평가액을 모르면 amount를 비운다. 자료상 합계는 확인된 잔고 평가액만 통화별로 계산하고 미확인 계좌/평가액을 표시한다. 별도 `최근 종가 기준 평가`는 저장 수량이 유지됐다는 가정으로 시세 API의 최근 일봉 종가를 적용한다. 현금·확인 불가 항목은 제외하고 통화별 일부 합계와 비교 가능한 자료 평가액의 차이를 표시한다. 원본 잔고/원장은 바꾸지 않는다. 환율 변환·확정 수익률은 제공하지 않는다. 계좌별 기준일이 다르면 경고하며 단일 날짜의 가족 자산으로 표현하지 않는다.
- 거래 CSV는 기관의 안정적인 externalId를 필수로 받는다. 동일 ID·동일 내용은 중복, 동일 ID·다른 내용은 409다. 동시 저장도 계좌 문서/영수증/원장에 대한 Firestore 트랜잭션으로 직렬화한다. 파일 자체가 동일하면 수정 재업로드도 재반영하지 않는다. 기존 반영 내용 정정은 별도 절차가 필요하다.

## 지원 파일

수동 잔고는 `previewManualHoldings` JSON 요청으로 기존 계좌의 서버 검토 세션을
생성한 뒤 `validateImport` → `commit`으로 저장한다. 출처는 `manual-holdings-v1`이며
파일 업로드와 동일하게 최대 200행·전체 잔고 대체 정책을 따른다. 브라우저에 이미
조회된 snapshot을 사용하므로 입력 화면을 열거나 편집할 때 추가 GET은 없다.
검토 생성 시 기존 snapshot의 기준일·importedAt을 비교하고, 검토에 저장한 snapshot
해시를 commit 트랜잭션에서 재확인한다. 다른 작업의 잔고 변경은 409로 거절한다.
저장 완료 요청의 재시도는 기존 receipt로 중복 처리한다. 기존보다 새로운 기준일만
지원하며, 거래 추가·같은 기준일 정정·빈 잔고 저장·한 종목만의 증분 변경은 제공하지 않는다.
확인된 전체 목록에서 사용자가 삭제한 종목만 새 잔고에서 빠지고 거래 원장은 보존한다.

CSV 내보내기는 계좌별 최신 잔고 또는 정상 `entries` 원장을 사용한다. 거래는 기존 인증 GET API로 200행씩 조회하며 최대 10,000행까지 지원한다. 조회 전후 권한을 확인하고 실제 거래가 추가될 때 증가하는 계좌 `entriesRevision`을 비교해 동시 업로드 중 부분 자료가 내려받아지지 않도록 한다. 중복 파일·중복 거래만 확인한 저장은 revision을 증가시키지 않는다. 기존 계좌에서 해당 필드가 없으면 0으로 간주한다.

내보낸 CSV는 최대 20열이며 금융 행과 `asOf`, `source`, `csvEscaped`만 포함한다. 마지막 열의 `v1:열이름|열이름` 표시는 스프레드시트 수식 방지용 작은따옴표를 붙인 셀만 기록한다. 재등록 파서는 표시된 셀의 보호 문자 하나만 제거하므로 원래 작은따옴표가 있던 externalId와 구분해 중복·충돌 정책을 유지한다. 잘못된 버전·열·셀 표시는 임의로 추측하지 않고 거부한다. 업로드 행 수와 전체 잔고 교체 규칙은 달라지지 않는다.

표준 UTF-8 CSV v1:

```csv
date,symbol,quantity,amount,currency,type,externalId
2026-10-15,AAPL,2,500,USD,buy,provider-trade-001
```

잔고에서는 type·externalId 불필요. date는 모든 행이 자료 기준일과 같아야 한다. amount는 기준일 평가액이며, 거래 파일에서는 거래 금액이다. 소수 수량을 지원한다. 종목은 통일된 코드(필요하면 거래소 접두어/접미어), 현금은 CASH를 사용한다. 서로 다른 코드의 동일 증권을 자동 통합하지 않는다.

토스 거래 PDF는 기존 미국 증권/환율 열이 있는 텍스트 PDF 파서를 재사용한다. 알려진 ISIN은 stockMappings의 symbol로 변환하며 나머지는 검토에서 사용자가 확인한다. 원화 환산 거래 금액을 KRW 원장으로 기록한다. PDF에는 안정적인 공급자 거래 ID가 없어 날짜/코드/유형/수량/금액과 파일 내 동일 행 발생 순번으로 중복을 판별한다. 동일 거래가 여러 번 발생하고 조회기간이 달라지면 구별이 모호할 수 있으므로 고유 거래 ID가 있는 표준 CSV를 권장한다. PDF 행을 수정할 경우 자동 생성 ID도 원본 거래의 정체성에 맞게 확인해야 한다.

한국투자·키움 등 증권사 고유 CSV/XLS/XLSX/PDF, 토스 잔고 PDF, 스캔/OCR PDF, 토스의 모든 서식 변형은 지원하지 않는다. 파서에 아직 인식되지 않는 레이아웃은 완전 추출을 보장하지 않는다. 원본과 미리보기를 대조해야 한다.

## 이전·배포 방법

1. 새 API/정적 앱과 Firestore rules/indexes/TTL 설정을 테스트 프로젝트에서 함께 적용한다. 서버에 FIRESTORE_SA_KEY, 클라이언트에 기존 Firebase 설정이 필요하다. 키를 클라이언트에 넣지 않는다. 기존 규칙은 DivGrow와 공유하므로 동일 변경을 해당 저장소에도 동기화해야 한다.
2. 본인 가족·프로필과 빈 본인 계좌를 만들고 기관·명의를 확인한다. 계좌의 “보존 이전”에서 기존 portfolios 자료가 그 계좌 한 개에만 속함을 확인한다. 이전을 실행하면 원본 경로와 함께 별도 복사한다. 원본은 수정/삭제하지 않으며 반복해도 같은 문서 ID에 복사한다.
3. 기존 portfolios 원본 최대 100종목·180거래는 한 트랜잭션으로 이전한다. 초과 시 거부하고 원본을 보존한다. 대량 자료나 혼합 계좌는 계좌별 원본 파일로 재가져오거나 별도 감사 가능한 이전 작업이 필요하다.
4. 다른 레거시 저장소(userAssets, adminPortfolios, users/holdings)는 중복/명의를 자동 판별할 수 없어 자동 합치지 않는다. 기존 읽기 화면을 유지한다. 새 합산에 넣으려면 기관별 기준일 잔고를 확인하고 가져온다.
5. 이전 원장은 계좌의 “보존 이전 원장”으로 조회한다. 기준일 불명의 기존 잔고는 현재 자산으로 승격하지 않는다. 최신 전체 잔고 파일을 업로드해야 새 합산에 포함된다. 이전 원장을 새 entries에 자동 재반영하지 않아 금액 중복 집계를 방지한다.
6. 롤백 시 기존 화면/원본을 사용한다. 새 컬렉션은 삭제할 필요가 없다. 운영 데이터 이전은 실행하지 않았다. 배포 시 운영 규칙을 조회해 기존 권한은 유지하고 새 컬렉션 직접 접근 차단 규칙만 적용했다. TTL 설정 변경은 서비스 계정의 권한 부족(403)으로 적용하지 못했다. 검토/초대의 서버 만료 검사는 동작하지만 자동 삭제를 활성화하려면 Firestore TTL 관리 권한이 있는 운영자가 reviews.expiresAt 및 familyInvitations.expiresAt TTL을 설정해야 한다.

## 실제 증권사 API 전 확인

기존 Toss API 관련 코드는 확장하거나 새 계좌 권한에 연결하지 않았다. 기관별 계약/서비스 범위, 고객별 OAuth·인증/계좌 소유 검증, 성인 공유 동의·철회와 미성년 보호자 요건, 제공되는 계좌·종목·거래 고유 ID, 과거 원장/기초 잔고·기준시각, 배당·세금·수수료·이동·분할 의미, 정정 이벤트와 재조회 범위, 토큰 보관/회전/폐기, 보존기간·감사 및 호출 제한을 먼저 확인해야 한다. 서버 공용 자격증명만으로 모든 고객 계좌를 조회하는 구조를 신규 기능에 사용하면 안 된다.
