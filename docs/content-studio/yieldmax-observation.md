## 확인 시간과 기존 전체 수집

- 지정 요일 **19:45~20:30 KST, 5분 간격**으로 해당 그룹만 확인한다. 21:00에도 재확인한다.
- 미국 표준시에는 **20:45~21:30 KST** 구간과 **22:00** 재확인을 추가한다.
  관측한 한국시간 구간을 연중 유지하면서 DST 변경에 대응한다. 미국 시각에 맞춰
  공식 발표 시간을 추정하거나 기존 한국시간 구간을 없애지 않는다.
- 복구는 매일 **09:37·12:37·18:37·23:37 KST**에 실행한다. 토·일과 미국·한국
  휴장일에도 수집한다. Roundhill의 :17 복구와 시각을 나누고 원장 쓰기 잠금을 공유한다.
- 기존 `Content Studio provider refresh`의 YieldMax **월~금 07:15 KST 전체 수집은 유지**한다.
  신규 스케줄러 목록 밖 종목과 과거 자료를 보완한다. 자동 전체 수집 제거는 이 변경에 포함하지 않는다.
- 예약 cron과 최초 실행 `created_at`으로 그룹·기준일을 계산한다. 실행 대기나 재실행으로
  날짜가 바뀌어도 다른 그룹을 선택하지 않는다. 겨울 전용 슬롯이 불필요한 계절에는
  plan 단계에서 끝내고 외부 조회나 원장 잠금을 시작하지 않는다.

## 공식 이력 조회와 요청 수

전체 목록을 매번 탐색하지 않고 설정된 공식 펀드 URL
`https://yieldmaxetfs.com/our-etfs/{ticker}/`만 조회한다. `INYY`, `MUY`, `YSPC`, `YRAM`도
공식 목록에서 확인된 이름을 그대로 사용한다. 종목 검색 카탈로그의 신규 등록과
공식 분배금 수집 대상 설정은 별개이며, 이 실행에서 다른 종목을 자동 등록하지 않는다.

펀드 페이지의 배당 이력 표에 있는 **실제 발표일·배당락일·기준일·지급일·금액**만
대상 기간에 맞춰 저장한다. 페이지를 조회한 날짜를 발표일로 대신 사용하지 않는다.
펀드 페이지에서 대상 종목의 기록을 찾지 못한 경우에만 YieldMax 공식 News 아카이브에서
해당 그룹의 최근 공지를 보완 조회한다. 금액 없는 예정 행과 대상 기간 밖 과거 공시를
새 공시로 인정하지 않는다.

한 이력 페이지에 여러 날짜가 있으므로 발표일 후보마다 같은 페이지를 다시 받지 않는다.
전 종목이 미확인인 정상 관측 1회는 월요일 3회, 화요일 12회, 수요일 44회의 펀드
페이지 HTTP 요청이 필요하다. 그룹 전체를 한 번에 제공하는 공통 표 조회 1회를 뜻하지 않는다.
원장과 공개 스냅샷이 일치한 종목은 HTTP 요청이 0회이며 다음에는 미확인 종목만 조회한다.
오전 전체 수집으로 이미 반영된 자료도 같은 완료 검사로 건너뛴다.

6종목 이하씩 처리해 부분 성공을 보존하고, 실행당 최대 8개 배치를 처리한다.
수요일 43종목은 8개 배치로 확인할 수 있다. 배치별 180초 제한을 두고 실패 시
해당 주기의 나머지는 다음 실행으로 이월한다. 전체 워크플로우 제한은 30분이다.
대기열이 많아 처리 한도를 넘은 주기도 삭제하지 않고 이후 복구에서 순환한다.

## 휴장·이월·중복 방지

Roundhill과 `scheduled_observation.py`의 공통 복구 로직을 사용한다.
기준일 전후 **3달력일** 중 현재까지의 발표일을 탐색하고, 미확인 주기를 다음 실행과
다음 주에도 보존한다. 미국 영업일은 탐색 우선순위와 지연 경고 기준에만 쓰며,
휴일 달력으로 공시일을 자동 이동시키지 않는다. 한국 휴장도 수집 중단 근거가 아니다.
조기 폐장일에도 조회하며 공식 배당락일·지급일을 임의로 옮기지 않는다.

2개 미국 영업일이 끝난 후에도 미확인이면 `overdue`로 알리되 계속 복구한다.
4일 이상 실제 발표일이 바뀐 예외는 원래 주기를 자동 완료하지 않는다. 이전 주의 미확인
공시가 다음 주 조기 공시일 수도 있으면 `needs_review`로 남긴다. 확인된 공식 데이터는
공개할 수 있지만 주기 배정은 보류한다. 수동으로 연결한 발표일을 인접 주기가 재사용할 수 없다.

미확인 상태는 `var/content-studio/generated/yieldmax-observations.json`에 저장해 기존
R2 아카이브로 전달한다. Roundhill 상태 파일과 경로·공급자 표식을 분리하며 기존
Roundhill 상태 형식도 계속 읽는다. 두 스케줄러와 오전 전체 수집은 공통
`content-studio-state-write` 잠금으로 복원→수집→저장→공개 커밋을 직렬화한다.
원장 저장과 공개 스냅샷 검증에 성공해야 공개 데이터를 커밋한다.

## 수동 복구와 검증

Actions의 **Observe YieldMax announcements**에서 `auto` 또는
`group-3`·`group-1`·`group-2`를 선택한다. 특정 그룹과 `declarationDate`를 지정하면
공식 발표일을 직접 조회할 수 있다. 장기 이동은 `cycleDate`에 원래 기준 주기를 함께
지정해 연결한다. 날짜는 공식 자료 기준이며 미래 날짜는 허용하지 않는다.
자동 상태가 처음 생길 때는 직전 주기와 3일 이내의 다음 주기를 만든다.
오래된 중단 기간을 처음부터 복구할 때는 수동 주기를 지정한다.
`dryRun=true`는 기존 R2 원장을 복원해 읽기만 한다. 외부 공시 수집, R2 상태 저장,
공개 데이터 커밋을 모두 건너뛰므로 운영 자격 증명과 상태 접근 점검에 사용할 수 있다.

```sh
python scripts/content_pipeline/schedule_yieldmax.py --plan-only \
  --event-schedule '0,5,10,15,20,25,30 11 * * 1-3' \
  --scheduled-at '2026-10-27T11:05:00+00:00'
python -m unittest discover -s tests/content_pipeline -p 'test_*observation.py'
```

GitHub 예약은 지연·누락될 수 있으므로 정확한 분 단위 시작을 보장하지 않는다.
원격 수집기 실행과 R2 쓰기는 main 반영 후 실제 운영 검증이 별도로 필요하다.
실행 보고서는 `yieldmax-<run_id>` 아티팩트로 30일 보관한다.
