# 계좌 자료 흐름과 원금 규칙 대조

## 현재 실제 조회 경로

| 화면/자료 | 현재 읽는 경로 | 의미와 한계 |
| --- | --- | --- |
| 자산관리·보유 요약 | `familyPortfolio` → `/api/family-portfolio` → `investmentAccounts`의 snapshot | 저장 스냅샷. 최근 import 출처와 snapshot 출처가 다를 수 있음 |
| 선택 계좌 원금·자금 | `portfolioCapitalRequest` → `/api/portfolio-capital` → `entries`, `cashEntries`, `cashClassifications`, `fundingAllocations`, `cashFxLinks` | PDF/수동 장부와 별도 검토값. 현재 기본 회수 합계는 현금 분류 합계이며 매매 손익까지 반영한 최종 원금 아님 |
| PDF 원본 import | `/api/family-portfolio` review/commit → `entries` 및 보존 snapshot | 현금/종목 원장으로 투영. API 관측을 자동 덮어쓰지 않음 |
| 기존 시험/채택 FIFO 보고서 | `/api/portfolio-capital?view=fifo-report` → 별도 채택 장부·보정·비공개 보고서 | 다른 입력·검토 상태. 일반 계좌 snapshot과 같은 정본이라고 가정할 수 없음 |
| 이번 계좌별 API 수집 | 로컬 프로그램 → 공식 accounts/orders → 로컬 원문 + `tossApiObservations`/`tossApiBatches` | 해당 accountId의 미검토 관측. 주문은 개별 fill·현금 정산·배당 입금과 같지 않음 |

이번 변경은 새 API 관측을 기존 원금에 임의 합산하지 않는다. `AccountEvidencePanel`이
계좌의 최근 가져오기 출처, 보유 snapshot 출처/기준일, 기존 장부의 행별 출처와
API 관측을 한 곳에서 대조한다. `capitalImportProjection`은 종목 거래에도 원문 문서의
source를 전달한다. 이미 읽은 capital 응답으로 계산하며 별도 장부 fetch를 추가하지 않는다.
API 관측은 버튼을 눌렀을 때만 읽고 실패를 빈 원장으로 표현하지 않는다.

현재 기본 `capitalSummary`는 저장된 원금 입금/출금 분류 합계다. 기존
`tracePortfolioFunding`은 미분류 출금의 현금 재원을 비례 추정하고 거래 차익을 별도
profit으로 취급한다. 이는 새 요청의 출금 우선순위·매매 손익 규칙과 다르므로 최종
원금으로 무조건 신뢰하거나 이번 작업에서 과거 수동 확정을 다시 쓰지 않는다.
화면 제목을 `저장 분류 기준 원금 회수`로 명확히 하고 새 정책 후보를 별도로 보인다.

## 새 규칙의 읽기 전용 구현

`lib/principal-funding-policy.js`는 소수 문자열의 정확한 유리수 계산을 사용한다.
입력은 기존 계좌에 이미 채택된 거래·현금·분류이며 새 미검토 API 주문을 섞지 않는다.
원문·분류·승인값에 쓰지 않고 각 행의 자동 후보/수동 확정 보존/미확인 근거를 반환한다.

- 배당 재투자: 실제 순액이 확인된 배당 lot를 먼저 들어온 순서대로 사용한다. 배당을
  초과하는 부분만 추적 가능한 원금 lot에 연결하고, 나머지는 미확인으로 남긴다.
- 출금: 남아 있는 배당을 FIFO로 먼저 사용하고 그 다음 추적 가능한 원금을 사용한다.
  출처가 없는 나머지 금액만 사용자 선택 대상으로 남긴다. 원금이 있다고 가정해 채우지 않는다.
- 원금 재원 주식 매도: 취득 lot를 FIFO로 소진하고 실제 순정산액과 원가의 차이를
  원금의 실현 손익으로 기록한다. 매도대금을 새 외부 입금이나 배당으로 세지 않는다.
- 배당 또는 혼합/미확인 재원 주식 매도: 원가 근거는 보여주되 매도대금의 원금/배당
  귀속은 규칙 확인 전 보류한다. 차익·손실을 배당으로 추정 확정하지 않는다.
- 기존 명시적 수동 매수 배분·출금 분할은 유지한다. 확인된 현금 lot가 부족하면
  수동 결정 원문을 바꾸지 않고 그 근거 부족을 표시한다.

같은 계좌·통화만 계산하며 환율을 가정하지 않는다. 같은 날 순서가 불명확한 사건,
없는 기초 lot/정산액, 배당 취소, 연결되지 않은 이동/환전, 충돌한 같은 출처 ID는
불확실성을 표시한다. 현금 행의 배당/매도 사본은 종목 거래와 이중 합산하지 않는다.
API와 PDF의 날짜·금액 유사성만으로 같은 사건이라고 합치지 않는다.

현재 일반 계좌 capital API는 전체 현금 범위와 기초 원금/배당을 증명하는 계약이 없어
정책 preview에서 전체 `remainingPrincipal`은 null(미확정)이다. null을 0으로 바꾸지
않는다. 단위 테스트에서만 범위·기초 잔액을 명시적으로 제공해 전체 계산을 검증했다.
예상 배당이나 매수·매도 주문의 총액을 실제 세후 배당/순정산액으로 대신 쓰지 않는다.

## 계산 예시

| 입증된 사건 | 규칙 대조 결과 |
| --- | --- |
| 원금 입금 1,000 → 배당 60 → 배당 40 → 70 재투자 → 80 출금 | 재투자는 앞 배당 60+다음 배당 10. 남은 배당 30을 먼저 출금하고 원금 50 차감. 범위/기초 0까지 입증된 경우 남은 원금 950 |
| 원금 입금 100 → 10주 매수 원가 100 → 5주 순매도 60 → 나머지 5주 순매도 40 → 30 출금 | FIFO 원가 50씩. 손익 +10, -10은 원금에 반영. 배당 0, 남은 원금 70 |
| 확인된 원금 5·배당 2만 있고 10 출금 | 배당 2, 원금 5, 나머지 3만 미확인. 전체 원금은 미확정 |
| 배당 10으로 1주 매수 후 12에 매도 | 배당 재원 lot 원가 10은 표시. 12의 원금/배당 귀속은 사용자 규칙 확인 전 보류 |

실제 운영 자료에 위 예시의 완전성을 가정하지 않는다. 미확인 출금의 `미확인 나머지
검토·선택`은 기존 현금 편집기에 알려진 후보와 나머지를 초안으로 채운다. `미확인
나머지만 원금으로 선택`도 초안만 바꾸며 `배분 확정`을 눌러야 기존 인증 API로 저장한다.
이미 확정한 배분이나 편집 중인 초안은 자동 덮어쓰지 않는다. 일괄 원금 확정·DB
migration은 추가하지 않았다.

## 환전 연결과 통합 경계

최근 운영 PR #227의 `projectCashFxLinks`를 그대로 재사용한다. 같은 계좌/날짜/환율,
적합한 방향/금액, 양쪽 후보의 유일한 1대1 조건에서 자동 연결하고, 수동 검토에서도
유일한 짝은 기존 로직이 자동 연결한다. 여러 후보·부족한 근거는 사용자 선택으로 남긴다.
`ylfx_…`와 `origin:yieldloom_internal`은 앱 내부 연결 ID이며 실제 토스 거래 ID가 아니다.
등록 원문/분류 revision이 바뀌어 stale인 연결은 유효한 환전 근거로 승격하지 않는다.
이번 작업에서 환전 매칭 알고리즘을 복제하거나 새 ID 체계를 추가하지 않았다.

환전 쌍의 연결 확인과 환전 전 재원의 원금/배당 추적은 다른 문제다. 연결이 유일하다는
이유만으로 전체 원금 이력·미확인 기초 자금을 확정하지 않는다. 새 정책 preview는
검증된 환전 재원 이행이 아직 없는 경우 이를 미확인으로 남긴다.

안전한 다음 통합은 계좌별 원문 → 독립 금융사건(주문/체결/정산/배당/환전) → 직접
금융사 ID 또는 검토한 관계 → 승인 원장이라는 한 경로다. 기존 PDF와 API가 겹치면
원문을 둘 다 보존하고 관계를 연결해야 하며 합산하거나 자동 삭제하면 안 된다. 주문
aggregate만 확보한 경우 개별 fill 순서·원가를 만들어내지 않는다. 기존 승인값의 실제
전환은 누락 범위·기초 잔액·수수료/세금·환전 재원과 회귀 대조를 마친 뒤 별도 승인한다.
