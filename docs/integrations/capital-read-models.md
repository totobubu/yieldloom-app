# 원금·자금 공유 조회본

## 범위와 무효화

`/api/portfolio-capital?accountId=…`의 전체 응답과 imported entries를 계좌별
`investmentAccounts/{id}/capitalReadModels/`에 압축 저장한다. 서버만 접근하며 기존
Firestore rules의 investmentAccounts 하위 직접 접근 거부가 그대로 적용된다.
개인 원장·토큰·계좌 ID는 사용량 로그에 넣지 않는다. legacy portfolios 조회는 기존 경로다.

`ledger`는 entriesRevision, `response`는 entriesRevision + capitalRevision +
자동 분류 규칙 버전 + response 스키마 버전에 묶인다. 만료 시간이 없어 새 인스턴스,
5분 이후 요청, 브라우저 새로고침에서도 원장을 다시 읽지 않는다. 모든 요청은 계좌·가족
권한을 확인하며, 응답을 돌려주기 전에도 권한과 버전을 재검증한다. 기존 클라이언트
version 일치는 권한 문서 2개만 읽는다. 클라이언트 ledgerVersion 부분 응답도 유지한다.

원장 import/add/replace/void/restore는 기존 트랜잭션의 entriesRevision을 유지하고,
원금·현금·분류·메모·자금 배정·기초 원금·환전 승인/해제는 기존 capitalRevision을
유지한다. 분류 수정은 원장 조회본을 재사용하고 응답 조회본만 재생성한다.
원장 변경은 새 버전의 전체 원장을 한 번 읽는다. 증분 원장 재계산을 구현한 것은 아니다.
projection/환전/계산의 의미를 바꾸면 response 스키마 버전도 올려야 한다.

## 생성과 장애

계좌·모델별 120초 트랜잭션 임대를 얻은 실행자 하나만 생성한다. 경합 요청에는
503/CAPITAL_READ_MODEL_BUSY와 Retry-After: 5를 반환한다. 자동 폴링은 추가하지 않는다.
충돌·권한 변경은 409/403으로 실패하며 부분 결과를 정상 응답으로 반환하지 않는다.
임대 만료 후 새 실행자가 복구할 수 있고, 이전 실행자는 owner fencing으로 게시할 수 없다.
실패는 60초 대기하며, 쓰기까지 quota로 실패하면 기존 임대가 재스캔을 억제한다.

압축본은 SHA-256을 검증한다. 450KB 이하이면 manifest에 함께 저장하고, 초과하면
450KB 청크 최대 10개와 manifest를 한 트랜잭션으로 게시한다. Base64 문서 크기는
약 600KB 이하, 게시 요청 전체는 10MiB 미만이다. 모델별 압축 4.5MB/해제 64MB를
넘으면 잘라내지 않고 실패하며 같은 버전의 자동 재생성을 차단한다. 별도 용량 확대 검토가
필요하다. 청크는 고정 슬롯으로 덮어쓰고 줄어든 슬롯은 게시 트랜잭션에서 삭제한다.
새 manifest와 이전 청크가 섞인 조회는 재시도 가능한 오류로 끝난다. 성공으로 숨기지 않는다.
계좌당 두 manifest와 최대 20개 청크만 보관하므로 버전별 데이터가 누적되지 않는다.

## 운영 영향: 적용 전 확인 대상

이 변경은 운영 조회 시 **새 파생 문서를 쓰는 방식**이다. 배포 전에 해당 영향을 보고하고
승인 범위를 확인한다. 실제 운영 백필/테스트 쓰기는 아직 실행하지 않았다.
일괄 migration은 필요하지 않으며 최초 정상 GET이 해당 계좌를 lazy backfill한다.
GET 권한의 viewer도 서버를 통해 파생 조회본 생성을 유발할 수 있지만, 원장·승인값을
변경하거나 접근 권한을 얻지는 않는다. Auth/보안 규칙/원장/기존 데이터는 변경하지 않는다.

N=entries 문서 수, M=현금·분류·자금배정·환전 연결 네 컬렉션의 문서 읽기 수 합계
(빈 컬렉션도 1), L/R=ledger/response 청크 수(인라인 저장이면 0)로 두면:

| 동작 | 문서 읽기 추정 | 파생 문서 쓰기 |
| --- | --- | --- |
| 첫 생성 | N + M + 18 | 4 + L + R |
| 별도 인스턴스/새로고침, 버전 동일 | 5 + R | 0 |
| 클라이언트 version 동일 | 2 | 0 |
| 분류 수정 뒤 첫 조회 | M + L + 12 | 2 + R, 줄어든 청크 삭제 추가 |
| 원장 변경 뒤 첫 조회 | 첫 생성과 동일 | 첫 생성과 동일, 줄어든 청크 삭제 추가 |

트랜잭션 재시도·실패·경합은 추가 작업을 발생시킬 수 있다. 이 수치는 API의 문서 읽기
관측 추정치이며 실제 청구량, 인덱스 읽기·저장비 감소율이나 전체 앱 사용량이 아니다.
기존 4,855건 cold 관측 전체가 읽기 5.1만의 원인이라는 주장은 하지 않는다.

30,000행 합성 데이터는 첫 생성 30,022건, 별도 인스턴스 10건(응답 5청크),
동일 version 2건이다. 실제 계좌의 압축률/청크 수·M은 운영 쓰기 전 측정하지 않았다.
source 거래값·분류·환전/자금 계산은 기존 경로의 전체 응답과 동일함을 대조한다.

## 복구와 롤백

원장과 승인 문서는 건드리지 않으므로 파생 조회본만 폐기하고 다시 생성할 수 있다.
특정 계좌의 손상 모델을 복구하려면 쓰기 영향을 확인한 후 해당 `capitalReadModels`
manifest 두 문서와 그 청크만 삭제한다. 다음 정상 GET에 N+M 읽기와 위 생성 쓰기가
다시 발생한다. 임대 만료 전 강제 삭제는 중복 스캔 가능성을 고려한다.
일괄 삭제·자동 운영 재구축 도구는 추가하지 않았다.

코드 롤백 또는 서버 환경변수 `CAPITAL_DURABLE_READ_MODELS=false` 후 재배포하면
기존 5분 메모리 캐시 경로로 복귀한다. 추가 쓰기는 중단하지만 반복 스캔 위험이 돌아온다.
파생 문서는 원본이 아니며 남아 있어도 기존 코드와 충돌하지 않는다. rollback 후 원장을
변경했더라도 revision이 달라져 새 코드에서 이전 조회본을 재사용하지 않는다.

## 검증

`node --test tests/capital_read_model.test.mjs tests/portfolio_capital.test.mjs
tests/portfolio-capital-client.test.mjs tests/cash_fx_links.test.mjs`로 합성 대형 원장,
새 인스턴스, 반복/동시 조회, 분류 수정·거래 취소, 권한 취소, 생성 중 버전 변경,
손상 데이터, 기존 자금 계산과 환전 계약을 확인한다. 운영 계좌를 테스트 용도로 쓰지 않는다.

무료 읽기는 일 50,000건, 매일 태평양 자정 무렵 초기화된다.
[공식 Firestore quota 문서](https://firebase.google.com/docs/firestore/quotas).
2026-11-03/04는 PST이므로 UTC 08:00/한국 17:00 무렵이다. 여름에는 한국 16:00이다.
예정된 quota 초기화와 실제 오류 해소는 구분하며, 운영 응답 없이 복구 완료로 보고하지 않는다.
